Preserve Entity Name Variants as Aliases

kb_build.py Small change

skills/kb/scripts/kb_build.py · resolve_entities()

Goal

LLM extractors sometimes produce aliases that are only capitalisation variants of the canonical name — noise that pollutes the KB frontmatter and the "Also known as" line. Add a meaningfulness filter so only genuine alternative names (different characters, not just case) survive into KB metadata. Capitalisation-only variants are silently dropped; real abbreviations and expansions are kept.

Dropped (noise)

"Magic System" → alias "magic system"

"Dark Arts" → alias "Dark arts"

Same letters, same lowercase — just case

Kept (meaningful)

"postgres" → alias "PostgreSQL"

"Aes Sedai" → alias "Aes Sedai sisters"

Different lowercase — genuinely different form

The filter: _is_meaningful_alias()

One helper function, applied everywhere an alias is appended. The rule is simple: an alias is meaningful only when its lowercase form differs from the canonical name's lowercase. Since entity resolution already keys on name.lower(), capitalisation-only variants are already deduplicated — there is no reason to preserve them as aliases.

New helper — add near top of resolve_entities()

def _is_meaningful_alias(alias: str, canonical: str) -> bool:
    return alias.lower() != canonical.lower()

That's it. "PostgreSQL" vs "postgres" → lowercase differ → True. "magic system" vs "Magic System" → lowercase same → False.

Where to apply the filter

Three call sites in resolve_entities().

Site 1

Initial entity load — filter LLM-provided aliases (line 84)

When a new entity is stored for the first time, its extractor-provided aliases list may already contain capitalisation noise. Filter it on the way in. 

merged.setdefault("aliases", [])
merged["aliases"] = [
    a for a in merged.get("aliases", [])
    if _is_meaningful_alias(a, merged["name"])
]
Site 2

Alias-based merge — absorbed entity name (line 98)

When B is absorbed into A, B's canonical name is added to A's aliases. Apply the filter before appending. 

if other["name"] not in entity["aliases"] \
        and other["name"] != entity["name"]:
    entity["aliases"].append(other["name"])
if other["name"] not in entity["aliases"] \
        and other["name"] != entity["name"] \
        and _is_meaningful_alias(other["name"], entity["name"]):
    entity["aliases"].append(other["name"])
Site 3

Alias-based merge — absorbed entity's aliases (line 100)

B's own aliases are also propagated to A. Filter each one before appending. 

for other_alias in other.get("aliases", []):
    if other_alias not in entity["aliases"] \
            and other_alias.lower() != key:
        entity["aliases"].append(other_alias)
for other_alias in other.get("aliases", []):
    if other_alias not in entity["aliases"] \
            and other_alias.lower() != key \
            and _is_meaningful_alias(other_alias, entity["name"]):
        entity["aliases"].append(other_alias)

Name-based merge: no change needed

The original plan proposed capturing name variants from the name-based merge path (when two extractions share the same name.lower()). With the meaningfulness filter, this becomes a no-op: because entities are keyed on name.lower(), any two names that collide are by definition capitalisation-only variants — and the filter would always drop them. No code change needed in that path.

"Dark Arts".lower() = "dark arts"

"Dark arts".lower() = "dark arts"

Same key → same bucket → capitalisation-only variant → filter drops it → no alias

Scope — what stays the same

  • write_kb_page() — aliases already flow into frontmatter and body, no changes.
  • The extraction JSON format — aliases is an existing field.
  • build_slug_map() — already maps alias names to slugs for wikilink injection.
  • The type-conflict path — untouched.
  • KB frontmatter aliases: YAML block — already present and correct.

Tests to add

In tests/test_kb_entity_resolution.py

  • Meaningful alias is kept: extraction with name: "postgres", aliases: ["PostgreSQL"] → aliases == ["PostgreSQL"].
